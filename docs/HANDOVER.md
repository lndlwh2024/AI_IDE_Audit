## 4. 问题清单与证据

优先级用于后续排期：P0 表示阻断基本使用或使审计关键事实失真，P1 表示完整融合及可靠交付的必修项。以下均是待修问题，本次没有将其标为已解决。

### H01 · P0 · CLI 命令矩阵整体无法启动

**证据**：`archguard/adapters/codex/installer.py:5` 引用不存在的 `get_ide_audit_dir`，配置模块实际提供 `get_audit_root`。`cli/main.py` 在启动时导入全部子命令，因此连 `archguard --help` 都失败。

进一步直接导入子命令，`commands/audit.py:3`、`graph.py:3`、`history.py:3` 分别引用不存在的 `AuditEngine`、`GraphAnalyzer`、`LedgerAnalyzer`。实际对应模块采用函数式接口，历史命令还误将操作账本作为审计报告历史。

**影响**：install/audit/commit/graph/history 均不能按文档使用。修复一个导入错误并不能让整个命令矩阵恢复。

### H02 · P0 · MCP 导入失败，备用服务也不是完整协议实现

**证据**：`archguard/mcp/server.py:79–83` 使用底层 `mcp.server.Server`，却调用其不存在的 `@app.tool`。本次安装 MCP 2.2.0，复现全部 7 个 MCP 测试失败，异常为 `AttributeError: 'Server' object has no attribute 'tool'`。

备用 `FallbackMCPServer` 仅处理 `tools/list` 和 `tools/call`，没有初始化握手处理，工具列表缺少输入 schema；当前测试只检查内部字典和装饰器，未进行真实 STDIO 客户端握手。不能沿用旧文档“直接改用备用服务即可”的建议。

此外仅有 `run_mcp_server()` 函数，没有独立 MCP 控制台入口或 `__main__` 启动模块，安装器也没有配置启动命令。应采用选定版本官方 SDK 的完整服务方式，测试公开协议，停止依赖私有 `app.tools` 结构。

### H03 · P0 · 安装和 B 窗口调用仍为模拟，产品闭环不存在

**证据**：`installer.py:25–33` 只打印配置更新和 Skill 创建日志，没有注册 MCP、注入守则或初始化全部资产。Hook 安装返回值未被安装器检查。

`session_manager.py:16–51` 明写“假设的 API 地址”和“模拟 API 调用”：固定返回 `new_thread_id_123`，恢复及发任务直接返回 `True`，实际 HTTP 调用被注释掉；该模块自身也受 H01 的缺失路径函数阻断。没有生产调用方把 `CodexSessionManager` 接到 Hook 或审计流程。

**影响**：不存在已证明可用的 B 会话创建/恢复/发送/完成/答疑链路，也没有可验证的裁决结果持久化。不能将“返回成功”当作 IDE 中已经出现审计窗口。

### H04 · P0 · Diff 事实不完整，内容规则漏检

**证据**：`core/diff_analyzer.py:152–158` 调用 `parent.diff(current)` 获取文件差异，后续从未生成的 patch 内容计算增删行数。`FileChange` 没有 `diff_content` 字段，但 MCP `get_file_diff` 访问此字段。

**复现**：普通提交将 `service.py` 的一行改成三行，Git `--numstat` 为 `3 / 1`，审计报告却为 `0 / 0`。提取原 `get_file_diff` 函数体执行，返回缺少 `diff_content` 的异常文本。

`architecture_detector.py:138–175` 将 `content_patterns` 匹配到文件路径，未匹配改动内容。相同提交在普通文件中加入 `import asyncio` 和 `CREATE TABLE`，架构信号仍为空。

**影响**：九大维度只是规则定义已存在，不等于九大维度检测完整实现；B 缺少逐文件核验与行号出入所需的原始证据。

### H05 · P0 · 审计与读取混用，重复审计会丢失或串用需求

**证据**：MCP `audit_changes` 直接调用 `run_audit`；后者读取当前 pending 并调用 `archive_and_clear`，随后重写 latest/history。没有以 commit 关联的不可变输入读取流程。`get_prompts` 也只读取当前 pending。

**复现**：同一 commit 第一次审计包含 1 条需求，第二次变为 0 条；之后记录一条“下一次尚未提交的需求”，再审计旧 commit，该需求被归到旧 commit 并清空。

**影响**：Hook 先审计、B 再调用工具时，B 可能拿不到本轮需求；快速连续开发或用户追问可能消费下一轮需求。账本和图谱同样读取工作区当前文件，未证明它们属于被审计的提交。

`prompt_store._write_json`、`engine._write_json` 实际直接覆盖写入，并不是注释宣称的原子替换。归档清空先于结果保存，且缺少整体事务和并发保护，需要一并修复。

### H06 · P0 · 图谱同步工具未完成初始化或增量扫描

**证据**：`sync/graph.py:24–29` 在无图谱时返回一个空 `CodeGraph` 对象，该对象为真值；MCP `sync_graph` 的 `if not graph` 初始化分支不会被触发。后续只是把刚读出的同一张图再写回，没有扫描源码变化。

`server.py:111` 传入 `trigger_version=None`，而 `GraphChangelogEntry.trigger_version` 要求字符串。图文件先写入，再因变更日志模型校验失败而报错。

**复现方式说明**：由于整个 MCP 模块已被 H02 阻断，本次单独提取原函数体，去掉注册装饰器后检查其下游行为；这不是协议验收。新项目有 `x.py`，调用结果为校验错误，图谱节点数仍为 0。

### H07 · P0 · 图谱基线、边标识及“违规”定义不正确

**证据与复现**：

- `engine.py:137` 没有传入旧图；`graph_analyzer.py:146–147` 默认为空图。只修改 README 的提交也把既存 `a.py`、`b.py` 报为新增节点。
- AST 产物使用文件路径作为节点键，例如 `a.py`，却把导入名 `b` 作为边终点。真实 `a.py → b.py → a.py` 相互导入被记录成 `a.py → b`、`b.py → a`，循环检测结果为空。
- `ImportFrom` 没有完整解析相对级别、包和导入成员；节点的 `module` 等于各自文件路径，缺少真正的模块划分。没有声明支持 Python 之外语言的解析能力。
- `check_cross_module_dependencies` 只要源/目标模块不同就列为违规，未结合允许依赖或分层规则。跨模块关系本身不能直接证明越权。
- 扫描排除规则检查绝对路径部件：实验项目只要位于名为 `.ide_audit` 的祖先目录下就被整体跳过；实际 `.venv` 目录却不在其排除名单中。

**影响**：既可能把历史结构误当本次变更，也可能漏掉真实环路。手工构造的理想图测试通过，不能证明 AST 生成图与分析器联动正确。

### H08 · P0 · 账本未限定本次提交，行号核验是占位

**证据**：`engine.py:159–163` 读取账本全部行，没有使用 `git.base_commit/head_commit`、提交边界或事件区间筛选。`ledger_analyzer.py:52–75` 的行范围逻辑保留 TODO 和 pass，始终返回空偏差列表。

**复现**：只提供上一次提交对 `main.py` 的申报，本次再次修改该文件且没有新申报，核验仍得到 `is_consistent=True`、评分 1.0。相反，历史中本次没有改动的文件也会被混入“虚报”集合。

另给出实际第一行变动的 patch，却申报 `999-999`，核验仍返回完全一致。该结果不能用于证明本次无未声明改动或无行号偏差。

### H09 · P1 · 锁、游标、流水和命名工具没有形成完整协同事务

**证据**：`LedgerManager.append_event` 的“读最新版本 → 分配版本 → 追加”没有锁。`CursorManager.update_cursor`、`GraphManager.update_graph` 将加锁责任留给调用者，但 MCP 没有实际组织锁事务。`AuditLogManager`、会话命名和未读游标流程没有接入 A 窗口工具调用链。

**复现**：在两个调用者都读取完最新版本后同时追加，两条账本事件均为 `v0001`。这是对真实竞争窗口的受控复现，不是生产压力测试。

因此旧文档“版本严格自增”“六步 RMW 已完成”“自动生成流水与状态快照”的描述不成立。还需核验持锁者身份、过期清理竞争、路径约束、游标回退和异常恢复。

### H10 · P0 · B 只读边界及证据不足状态没有落实

**证据**：MCP 将 A 写工具和 B 读工具注册到同一工具集合，没有角色授权边界；B 查询图谱/账本会实例化带目录创建副作用的管理器，`audit_changes` 更会消费需求并写入结果。会话管理器没有设置真实只读沙箱。

图谱和账本损坏时，引擎只写日志并返回空字典；报告模板会省略该节。实验中账本为无效 JSON，报告没有结构化的错误/完整性字段，需求流程仍继续归档。

**影响**：现状没有证明“B 查询无副作用”，也不能让 B 明确区分“没有变化”和“没有审计到”。这里的角色边界是 V2.0 交付要求，不等于断言当前已经发生越权写入。

### H11 · P1 · B 模板偏离双尺度裁决要求

**证据**：`templates/skill_codex_audit.md:9–11` 将宏观判断写成“是否符合现有架构图谱”，微观判断写成“被修改的文件之间是否强关联”。

正确基准应是**用户本轮原始需求**：用户明确授权时可以合理修改现有架构；多个文件彼此相关，也可能整体与需求无关。模板还缺少逐文件需求证据、结构化裁决资源清单、证据不足处理，以及完成报告后持续答疑的明确协议。

### H12 · P1 · Hook 和提交兜底不可靠

**证据**：`adapters/git_hook.py` 直接覆盖 `.git/hooks/post-commit`，卸载时直接删除，没有管理自己的标记区块或保留既有 Hook；假定 `.git` 是目录，未处理 worktree 的 gitdir 文件和自定义 hooksPath。Hook 仅调用当前已坏的 `archguard audit`，未绑定解释器和目标提交，也未对接 B。

`cli/commands/commit.py` 只运行 `git commit`，没有实现文档承诺的自动暂存或无 Hook 兜底；若干 CLI 捕获错误后只输出文本，缺少可靠非零退出状态。

**影响**：不能声称安装或提交后必然触发成功。post-commit 发生在提交之后，审计“不合理”只能报告/提示，当前设计并不阻止该 commit 已经落地。

### H13 · P1 · 迁移脚本不能承诺无损迁移或原 Skill 已下线

**证据**：`scripts/migrate_ai_sync_to_ide_audit.py` 遇到 `.ai-sync.bak` 会递归删除旧备份；向已存在的 `.ide_audit` 用合并复制覆盖同名文件。没有 schema/版本校验、内容哈希清单、冲突保护、事务回滚或旧规范引用处理。

当前只能认定“有目录复制及 dry-run 分支”。不能认定资产无损、可恢复，尤其不能直接用于已在写入的新目录。实际迁移及破坏性分支本次未执行。

### H14 · P0 · wheel 缺少运行必需资源

**证据**：按当前 `pyproject.toml` 成功构建 `ide_audit-0.2.0-py3-none-any.whl`，检查归档内容：无 YAML 文件、无模板文件，只有 `archguard` 一个控制台入口。

`rules/loader.py` 要求读取包内 `default_rules.yaml`；`report_generator.py` 依赖源码仓库根下的 templates。前者在缺资源安装中会阻断引擎，后者可能降级输出，但不代表安装包完整。源码目录的 editable 测试无法替代 wheel 安装验收。
