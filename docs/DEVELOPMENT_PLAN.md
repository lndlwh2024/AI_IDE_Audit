## 1. 目标与实施原则

交付一个可安装、可重复审计、可持续答疑的 IDE_Audit 插件。它完整承接 dual-agent-sync 的图谱、协同记账、游标、锁及配套工作流，并在用户提交后完成“本地事实分析 → Codex 独立 B 会话裁决 → 报告与答疑”闭环。最终用户只使用 IDE_Audit，不再单独安装 dual-agent-sync。

优先修复现有模块，不另建一套审计系统。Git diff 始终是最高权重事实，单次审计始终是触发时最后一次 commit 的第一父提交到该 commit；后续新增提交不能改变已开始任务的范围。根提交明确使用空树基线。

同一产品内按职责划分接口和持久化能力，不等于拆成两个独立插件。以下内部模块和数据结构是已确认的设计目标，已实现部分与未完成部分以顶部进度表为准。

## 2. 开发前需要固定的契约

### 2.1 原 dual-agent-sync 完整能力基线

当前代码中的 17 个模型不是“100% 继承”的验收依据。先归档原 Skill 的准确版本或内容哈希、资源文件、事件例子和正常工作流程，建立以下映射表；从原材料识别出的其他能力也必须纳入，不以此表作为删减范围的理由。

| 能力 | 建议责任位置 | 必须证明的行为 |
|:---|:---|:---|
| 事件字段、诊断记录、上下文交接 | `sync/schemas.py` 及协同服务 | 历史数据完整保留；有效/无效数据按规则处理 |
| 追加式账本、版本和行位置 | `sync/ledger.py` | 多写入者版本唯一、顺序可验证、错误可恢复 |
| IDE 命名、会话 ID | `sync/naming.py` | 规则一致、会话隔离、并发不碰撞 |
| 游标增量读取、回退、会话合并 | `sync/cursor.py` | 不覆盖其他会话进度，不漏读，异常恢复有证据 |
| 编辑意图、游标锁、图谱写锁 | `sync/lock.py` 及业务事务 | 所有正式入口实际调用锁；竞争和释放语义明确 |
| 图谱初始化、增量、职责及拓扑 | `sync/graph.py` | 文件/模块/边对应正确；保留原有人工语义字段 |
| 图谱变更日志及事件关联 | 图谱/账本事务 | 图与日志可追溯到同一操作和提交 |
| AUDIT_LOG、PROJECT_STATE | `sync/audit_log.py` | 由正式事件链生成或更新，失败可重建 |
| 原 Skill 的操作顺序和交接规范 | 插件内统一 A 守则及工具 | 新会话能读取未读信息并完成同等工作流 |
| 历史目录与规则切换 | 迁移及安装器 | 数据、引用与启用状态统一切到 IDE_Audit |

如果旧能力覆盖多种语言，不能将当前 Python-only 扫描当成完整替代。语言支持、图谱字段和忽略规则以原基线验收；未支持项显示为覆盖不足，不能静默丢弃。

### 2.2 提交、需求、账本和图谱绑定

建议引入一个明确的审计任务描述：

| 字段 | 含义 |
|:---|:---|
| `audit_id` | 本次任务标识，绑定项目及目标提交 |
| `base_commit` / `head_commit` | 触发时固定的完整 SHA，后续工具不得重新解释 HEAD |
| `prompt_ids` / `batch_id` | 两次提交间全部用户需求的固定集合 |
| `ledger_range` / `event_ids` | 本次申报事件集合及边界，不使用全部历史账本 |
| `graph_before` / `graph_after` | 与两个代码版本关联的图谱快照或可验证来源 |
| `schema_version` / `input_hashes` | 数据格式和输入完整性检查依据 |
| `analysis_status` / `diagnostics` | 成功、部分证据缺失或执行错误，以及具体原因 |

采用“开发批次 → 提交时封存 → Hook 绑定实际 SHA”的流程。提交前不可能知道最终 commit hash，不要要求 AI 猜测或反复改写 append-only 历史事件。优先用独立批次清单/关联事件完成绑定。

`.ide_audit` 当前被忽略，不应假定每次提交树中必然存在完整图谱和账本。可由 A 维护工作态，并由编排层封存带来源哈希的快照；缺失或过期时，从固定提交的源码重建可计算的拓扑，人工职责/申报信息标为缺失。不能拿当前工作区图谱冒充历史基线。

手动 `audit` 同样只启动当前最新提交的审计；若对应需求批次不存在，返回明确的证据不足流程状态。不能为了填满报告自动消费当前 pending。审计任务已固定后，B 追问该任务的旧文件是证据查询，不是扩大审计范围。

### 2.3 写权限与持久化边界

| 层/角色 | 允许的行为 | 验收要求 |
|:---|:---|:---|
| A 开发会话 | 用户授权开发、调用协同维护工具 | 业务代码修改仍由开发 AI 完成 |
| `sync/` | 写 `.ide_audit` 内图谱、账本、游标等协同资产 | 统一受控路径、锁和事务，不修改业务源码 |
| `core/` 分析函数 | 读取固定事实，返回结构化分析值 | 无源文件/图谱修改，无隐式建目录、归档、清空 |
| 编排/存储层（建议新增最薄一层） | 固定输入、封存需求、保存事实包和裁决、任务状态 | 写入仅限明确的审计元数据区域，失败可重试 |
| B 审计会话 | 读取绑定任务的事实与源码，输出裁决、回答追问 | 实际沙箱只读，仅可见审计读工具，无 A 写入口 |

V2.0 一方面称 core 只读，另一方面要求保存报告并包含 prompt_store，存在职责表达不一致。建议以“分析只读、持久化由编排层承担”消除歧义，将现有相关函数迁移或封装到适当层；这是小范围职责整理，不变更双窗口和两阶段架构。

同一 Python 包可以提供不同角色的服务实例或受控工具列表；角色由宿主可信配置决定，不能让调用者通过传入 `role='dev'` 自行升级。B 的只读沙箱也不能替代外部 MCP 写工具权限控制，两层都要验证。

## 3. 具体开发方案

### 3.1 恢复入口、固定 SDK 与资源打包

- CLI 对接已经存在的函数式接口：audit 调用编排入口，graph 读取图谱摘要，history 查询提交关联的审计结果和裁决；统一非零错误退出。
- 统一配置路径函数，校验项目和 Git 仓库位置；避免一个可选功能导入失败阻断全部帮助命令。
- 根据验证过的官方 MCP SDK 版本实现完整 STDIO 服务，增加可安装的启动入口；固定支持范围并记录测试依赖版本，不能继续使用没有上界的依赖范围宣称兼容。
- 工具注册、参数校验、错误返回以真实客户端握手和调用结果验收。删除或明确降为开发辅助的伪 MCP 备用实现。
- 规则和模板纳入包资源，改用安装环境可定位的资源加载方式；开发者守则与审计守则随同一产品分发。

对应问题：H01、H02、H14。

### 3.2 修复确定性事实提取和规则检测

- 一次解析目标 SHA，提取真实文件状态、rename 来源、numstat、patch 和 hunk。保留旧侧/新侧行坐标，供行范围核验和 B 定位。
- 明确二进制、模式变化、子模块、根提交、删除及重命名行为，无法提供文本 patch 时输出原因。
- 内容规则扫描实际增删代码；结构规则使用代码树事实。保留“客观信号”的表述，不把路径命中当成已经证明的架构破坏。
- 账本按冻结事件范围核验，区分新增/删除/重命名和文档声明，解析行范围而非只算文件集合。
- 对 `lines=None`、坏行、未知字段/版本、路径差异给出明确诊断；缺资料时不输出完全一致结论。

对应问题：H04、H08、H10。

### 3.3 修复图谱生成、增量维护和比较

- 为工程内依赖统一节点标识，例如仓库相对 POSIX 路径；工程外依赖单独标记，不伪装成项目文件节点。
- Python 解析补齐包、相对导入及导入成员解析；扫描忽略规则基于项目相对路径，覆盖虚拟环境、构建产物等；其他语言按原 Skill 基线补齐。
- 将“从源码扫描得到新图”和“提交新图及日志”分开，增量操作确实读取受影响文件；无图时可靠初始化。
- 新旧图都绑定目标提交；增量结果与完整重建结果应一致。只改 README 不得重报全部代码节点。
- 模块归属和允许依赖来自明确配置或原有图谱，不把每个文件当作独立架构层。普通跨模块边输出为事实信号，违反显式规则才标记规则违例。
- 保留已有 purpose/exports 等语义信息，对删节点相关模块和边变化计算影响范围。

对应问题：H06、H07。

### 3.4 补齐协同事务与一次性需求封存

- 在正式写入口统一执行账本版本分配锁、游标 RMW 和图谱写锁；锁所有者带唯一持有标识，校验释放和过期回收条件。
- 使用唯一临时文件和原子替换保护快照；append-only 账本在锁内追加，检测部分行和版本损坏。多文件事务用可恢复记录处理，不能声称一次 replace 就保障所有资产原子一致。
- 一个标准事件驱动账本、图谱影响、流水/状态更新及相应游标推进；任一失败必须可报告、可恢复，不能返回假成功。
- prompt 追加、封存和下一批接收有独立边界。每个 commit 首次固定输入后，重审读取同一封存内容，不再次清空 pending。
- `audit_changes`、`get_prompts`、`get_file_diff`、`get_architecture_graph`、`get_ledger_records` 查询同一 `audit_id` 的快照；读取不得重跑写流程。
- 所有外部输入路径和 IDE/scope 标识经过规范化校验，写路径必须停留在被授权的元数据目录内。

对应问题：H05、H09、H10，以及完整融合能力基线。

### 3.5 Codex 接入：先验证宿主，再接入主流程

本机只读检查得到 `codex-cli 0.153.4`，`app-server --help` 提供 STDIO 等传输选项。官方文档描述 `initialize` / `initialized` 握手、`thread/start` / `thread/resume`、`turn/start` 以及完成事件和沙箱策略，不能使用当前代码假设的 localhost HTTP 路径。具体字段应从目标安装版本生成 schema 并验证。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

上述资料说明协议能力，不证明插件启动的任意 app-server 子进程都会自动出现在用户当前桌面任务列表。把“真实 B 会话能被桌面显示、接续和恢复”列为最早的技术验证门。

技术验证产物必须包括：真实会话 ID、请求/响应与完成事件记录、桌面中独立 B 会话的可见证据、一次追问、关闭连接/重启后的恢复，以及只读操作限制。验证使用既有 Codex 登录和模型配置，不增加外部 LLM API 调用或 API Key 依赖。

实现要求：

1. 固定项目对应 B 会话，创建时不复制 A 历史；复用只保留 B 审计历史。检查项目身份，避免跨项目错误复用。
2. 每次任务绑定明确提交和输入快照，并保证历史审计不会污染本轮需求判断。
3. 正式会话仅启用只读能力；读取项目 AGENTS 时不得使 A 的自动 commit 守则变成 B 的开发任务。
4. 发送成功、轮次开始和裁决完成是不同状态；监听实际完成/失败事件，持久化真实裁决，不能仅记录函数返回 True。
5. 支持任务排队、忙碌检测、断线恢复、过期 threadId 和重试去重。创建失败不能伪造 ID 或降级成自审。
6. 完成后保持用户可继续追问的会话；短时 CLI 进程退出不等于终止 B 的可恢复生命周期。

如果目标桌面版本无法通过已验证方式满足可见 B 和持续答疑，应形成明确技术结论，先调整适配方案；不能用命令行模型输出冒充已经达成桌面双窗口需求。

对应问题：H03、H10。

### 3.6 恢复准确的 B 双尺度裁决

B 的输入以用户需求原文和固定提交事实为依据。输出至少包括：提交标识、总体裁决、需求引用、架构信号逐项解释、每个改动文件与需求的关系、记账出入核查、理由与具体证据位置。

- 宏观问题是“架构变化是否获得本轮需求授权”，不只是“是否符合原架构”。
- 微观问题是“每个改动文件是否与本轮需求强相关”，不只是“文件之间是否相关”。
- 先核实未声明原因及实质，不能把数据缺失直接命名为恶意瞒报。
- 保留 V2.0 的“合理/不合理”裁决体系。必要证据缺失时显示流程未完成/需补证据，不自动判为合理，也不在本计划中擅自新增第三种业务裁决。

对应问题：H11，并贯通 H04–H10。

### 3.7 安装、Hook、迁移与下线

- 安装器先检查环境并生成操作计划，事务化应用自己的 MCP 配置和守则标记块，保留用户现有内容；反复安装/卸载不重复、不误删。
- 使用 Git 解析出的有效 Hook 路径，支持 worktree 和 hooksPath；链式保留既有 Hook，固定解释器、项目根和目标 SHA。Hook 只触发一次本次任务，失败保留事实/队列并给出可见诊断。
- 明确 `commit` 自动暂存范围及已有变更归属，落实文档兜底行为；不要把与本轮无关的工作区变更顺带提交。
- 迁移先生成不可覆盖的备份和哈希清单，检查目标资产冲突、schema 和路径引用，提供回滚记录。旧数据不得因重试而失去上一份备份。
- 在临时副本做 dry-run 和实迁移验证，确认等价和可恢复后，再切换目标项目规范与数据来源。下线独立 Skill 时只处理已确认归属的旧规范/安装引用，不删除审计备份。
- 发布统一安装产物和升级说明，通过 GitHub 审查与发布流程交付；没有验证 PyPI 发布前，不把 `pip install ide-audit` 写成已证实可用的安装方式。

对应问题：H12、H13、H14。

## 4. 分阶段开发计划

以下为一名熟悉 Python、MCP 和 Codex 的开发者的初步工作量估算，不是已经完成的进度或确定日期；原 Skill 材料不齐、桌面接入方式变化会影响工期。每阶段完成后复核 HANDOVER，只按通过的验收门更新状态。

| 里程碑 | 顺序与工作量 | 工作包 | 退出条件 |
|:---|:---|:---|:---|
| M0：固定契约与接入验证 | 首先，2–3 人日 | 原 Skill 能力清单；固定数据契约；真实 Codex B 技术验证 | 桌面可见独立 B、只读和追问路径有证据；能力基线可追溯；不确定项列清 |
| M1：恢复可安装入口 | M0 后，2–3 人日 | H01/H02/H14：CLI、MCP、SDK 支持范围、包资源 | 从 wheel 在隔离环境启动 CLI 和 MCP；客户端能握手列工具；不伪报完整审计可用 |
| M2：修复审计事实与输入绑定 | M1 后，5–7 人日 | H04/H05/H08/H10：固定 SHA、patch/hunk、内容规则、本次账本、需求快照 | 与 Git 事实一致；同 commit 重审结果输入相同；新需求不被旧任务消费；证据缺失显式输出 |
| M3：完整协同与图谱融合 | M2 后，5–8 人日 | H06/H07/H09：真实增量图、基线拓扑、锁事务、游标、日志、命名及原 Skill 等价 | 原能力清单逐项通过；真实扫描到分析器联动正确；并发和故障恢复通过 |
| M4：完成 A/B 产品闭环 | M3 后，4–6 人日 | H03/H10/H11/H12：统一守则、安装/Hook、正式 B 生命周期、裁决保存 | 一次开发提交自动进入独立 B 并完成双尺度报告；连续提交、追问、重启恢复可用 |
| M5：迁移、发布和旧 Skill 下线 | M4 后，4–6 人日 | H13/H14 及全量验收、真实资产迁移副本、文档和发布包 | 下节验收全通过，迁移可回滚，统一插件发布材料就绪，独立 Skill 不再是运行依赖 |

合计约 **22–33 人日**；另留约 20% 兼容性及联调余量，初步安排约 **27–40 人日**。M0 后按实际接入结论和旧能力差额重估，不能仅凭现有文件数压缩为“修几个测试即可发版”。

第一轮建议交付边界是 **M0 + M1**：把接入可行性、入口和安装资源做实，并把本次已复现的错误固化为后续回归场景。之后按 M2–M5 推进，不提前宣称四阶段全部完成。

版本建议：入口修复先作为后续开发版，事实与协同完成后作为内测版，完整闭环后才做候选发布。具体版本号由发布时已有标签和远程状态确定；本计划没有创建标签或承诺已经发布任何版本。

## 5. 最终验收清单

### 5.1 本地事实与完整协同

- [ ] 根提交、普通提交、删除、重命名、合并第一父基线、二进制等事实与固定 Git SHA 一致。
- [ ] 普通路径中的建表、路由、执行模型等内容变化可检测，报告能返回对应增删行证据。
- [ ] 完全相同代码图在文档提交中不报新拓扑；真实相对导入和环路测试通过。
- [ ] 旧账本不能抵消本次未声明改动；虚报、行范围偏差和重命名声明有确定结果。
- [ ] 重复读取和重审不改变 prompt、ledger、graph；下一批需求和连续提交不会串用。
- [ ] 所有原 dual-agent-sync 能力都有原条目、正式调用入口和验收结果，无未解释的功能删除。
- [ ] 多进程竞争、部分写失败、过期锁、坏 JSON/账本行、游标异常可诊断且可恢复。

### 5.2 双尺度业务场景

| 场景 | 期望行为 |
|:---|:---|
| 需求要求合法架构重构，文件均相关、申报准确 | B 判合理，列出需求授权和逐文件支撑 |
| 架构修改合理，但夹带无关业务文件 | B 判不合理，指出无关文件和具体变更 |
| 只要求修日志，却改数据库结构 | B 判不合理，说明需求与架构变化的差异 |
| 本次未声明核心文件修改 | 本地准确列出出入；B 依据真实需求和证据裁决 |
| 图谱/需求/账本不足或损坏 | 显示未完成/需补证据，不伪装为通过 |
| B 完成后继续询问争议文件 | 在同一会话基于同一任务 SHA 回答，无写副作用 |

B 的语义验收采用固定需求与提交样例，检查裁决、文件覆盖和证据正确性，不要求自然语言逐字一致；保留实际模型/客户端版本和审查记录。

### 5.3 安装、权限与交付

- [ ] 从干净 wheel 安装，默认规则、模板、CLI、MCP 均可运行，不依赖源码工作目录。
- [ ] 安装、重复安装、卸载保留用户已有配置、AGENTS 和 Hook；Windows 空格/中文路径、worktree、hooksPath 验证通过。
- [ ] B 工具列表不包含写入口，真实沙箱拒绝写源码；查询前后源码和协同输入哈希不变。
- [ ] Hook 连续触发、B 忙碌、失效 threadId、断线、IDE 重启均有明确恢复行为和可查询结果。
- [ ] 迁移 dry-run 零变更，实迁移不会覆盖已有备份或目标资产，校验和回滚测试通过。
- [ ] 新统一守则及插件已承接全部旧流程，运行不依赖 `.ai-sync` 或独立 dual-agent-sync Skill。
- [ ] GitHub CI 覆盖选定 Python/依赖版本、Windows 测试及 wheel 安装冒烟；发布说明、升级说明、限制清单与实际结果一致。

## 6. 每次开发交接应提交的材料

每个工作包附上需求/缺陷编号、修改文件范围、真实测试命令与结果、安装或运行证据、剩余限制和回滚方式。修改完成后给出功能审计清单；代码、测试与文档一同评审，不能通过削弱断言或跳过关键测试来换取“全绿”。

交接状态使用“待开发 / 实现中 / 待验收 / 验收通过”。模块存在或单元测试通过只允许进入待验收；只有对应里程碑和真实用户流程验收通过，才可更新为完成。Git push 成功后再报告实际版本与变更内容。
